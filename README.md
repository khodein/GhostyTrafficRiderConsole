# Ghosty Traffic Rider Console

Личный TUI-менеджер для разворачивания и обслуживания proxy/VPN-серверов
(сейчас: Shadowsocks+v2ray-plugin, VLESS+Reality) и генерации готовых
профилей для Clash Verge.

Состоит из двух частей:

- **`ghosty_console/`** — TUI-приложение (Python, Textual). Хранит список
  твоих серверов, по SSH разворачивает/проверяет/откатывает конфиги.
- **`proxy-scripts/`** — сами bash-скрипты, которые всё это делают. Работают
  сами по себе, без TUI (можно запускать руками с ноутбука).

TUI — это просто удобная обёртка вокруг `proxy-scripts`: каждое действие в
интерфейсе (Deploy, Verify, ...) в итоге вызывает те же скрипты, что лежат
в `proxy-scripts/`.

## Быстрый старт

```
./start.command
```

При первом запуске сам создаст `.venv` и поставит зависимости
(`requirements.txt`: textual, paramiko, pyyaml), дальше просто открывает TUI.

Ручной запуск:
```
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
.venv/bin/python run.py
```

## Модель данных

Двухуровневая модель, отдельно "сервер" и "прокси на нём":

- **Сервер** (`ServerProfile`) — это просто SSH-подключение: host, user,
  port, путь к ключу (или пусто — тогда пароль спрашивается перед каждым
  действием). Никакого провайдера или порта прокси на этом уровне нет.
- **Прокси** — то, что реально развёрнуто на сервере: конкретный провайдер
  (`shadowsocks-xray`, `xray-reality`, ...) со своим портом, сертификатом
  и т.д. У одного сервера может быть 0, 1 или несколько прокси
  одновременно (см. "Несколько прокси параллельно на одном сервере" ниже).

## TUI: экраны и клавиши

### Список серверов
- `a` — добавить сервер (имя, host, ssh user/port, путь к ключу или пусто
  для пароля — без выбора провайдера, он не привязан к серверу). После
  сохранения сразу открывается карточка сервера и **автоматически
  запускается Discover** — никакого лишнего клика не нужно: вводишь
  host+пароль (или указываешь ключ) и сразу видишь список всех прокси,
  которые реально там развёрнуты, даже если их несколько на разных
  провайдерах — все они появляются в таблице внутри карточки ЭТОГО
  сервера, а не как отдельные записи в общем списке.
- `enter` — открыть карточку сервера
- `d` — удалить выбранный сервер целиком (только локально: сервер + все
  его прокси в локальном состоянии; на самом VPS ничего не трогает)
- `r` — обновить список

### Карточка сервера (дашборд)
Таблица прокси (провайдер / порт / домен-или-сайт) + кнопки **Discover**,
**Deploy new proxy**, **Delete server**, **Back** (`escape`/`b`).

- **Discover** — подключается по SSH и сканирует сервер на всё, что
  реально там развёрнуто (по любому провайдеру), подтягивает
  `client-info.json` для каждого найденного и приводит локальную таблицу
  прокси в соответствие с реальностью. Ключевой сценарий: с любого
  устройства ввести host+пароль и сразу получить рабочее состояние без
  необходимости помнить, что именно и как было развёрнуто.
- **Deploy new proxy** — открывает выбор провайдера + порта (пусто —
  случайный) и разворачивает новый прокси на этом сервере, добавляя его
  строкой в таблицу.
- **Delete server** — убирает сервер и все его прокси из локального
  списка (на сервере ничего не меняет).
- `enter` / клик по строке — открыть карточку конкретного прокси.

### Карточка прокси
Кнопки: **Deploy**, **Regenerate config**, **Ping**, **Verify**,
**Status / Logs**, **Rollback**, **Remove config**, **Delete proxy**,
**Back** (`escape`/`b`).

- **Deploy** — повторно заливает скрипты провайдера и перезапускает
  установку (идемпотентно — существующий порт не меняется), забирает
  свежий `client-info.json`, генерирует клиентский профиль и сохраняет
  снапшот (для Rollback).
- **Regenerate config** — пересобирает клиентский профиль (Clash YAML /
  share-ссылку), если потерял или забыл. Если `client-info.json` ещё
  лежит локально — работает мгновенно, без SSH и пароля. Если нет —
  сама подключается по SSH и подтягивает его заново с сервера.
- **Devices / Add device / Rename device / Remove device** — только у
  провайдеров с `remote/clients.sh` (сейчас `xray-reality`). У каждого
  устройства свой ключ (UUID) и своя ссылка: **Devices** открывает окно со
  всеми пользователями и их ссылками (стрелки — выбор, подсказка с полной
  ссылкой, `Enter` — скопировать ссылку в буфер обмена, `Esc` — закрыть; SSH
  не нужен), **Add device** спрашивает имя (до 32 символов: буквы любого
  языка, цифры, пробел, `_ - .`, например `Мой iPhone`) и выдаёт новую
  ссылку, **Rename device** меняет только название (UUID остаётся — уже
  импортированная ссылка продолжает работать), **Remove device** отзывает ключ
  только этого устройства — остальные ссылки работают. Название профиля в
  клиенте (Hiddify и др.) — `<имя сервера в консоли> · <устройство>`, например
  `gmail · Мой iPhone`; это подпись после `#` в ссылке, подключение от неё не
  зависит. Add/Remove перезапускают контейнер (соединения рвутся на 1–2
  секунды), Rename — нет; порт и ключи Reality не меняются. Прокси,
  развёрнутый до появления устройств, получает устройство `default` с прежним
  UUID — уже выданная ссылка остаётся рабочей, переимпортировать её не нужно.
- **Ping** — TCP-проверка SSH-порта и порта этого прокси (без SSH-логина).
- **Verify** — внешняя проверка последнего деплоя (без SSH — просто
  дёргает `proxy-scripts/verify.sh` локально с сохранённым client-info).
- **Status / Logs** — статус Docker-контейнера + последние строки логов
  по SSH, плюс что-то специфичное для провайдера (например для
  Shadowsocks — статус таймера продления сертификата).
- **Rollback** — выбор одного из сохранённых снапшотов этого прокси,
  откатывает файлы состояния на сервере и перезапускает контейнер.
- **Remove config** — останавливает контейнер и чистит файлы состояния
  на сервере (сертификаты и таймер продления, если есть, не трогает).
  Прокси остаётся в таблице (с историей снапшотов) до явного Delete proxy.
- **Delete proxy** — убирает этот прокси из локальной таблицы сервера
  (на сервере ничего не меняет).

Если у сервера не указан ssh-ключ — перед SSH-действием всплывает
модалка для пароля. Пароль хранится только в памяти на время действия,
никогда не пишется на диск.

## Локальное состояние

```
~/.config/ghosty-console/
  servers.yaml                       # список серверов (без паролей, без провайдеров)
  servers/<server-name>/
    proxies/<provider>/
      current/                       # что сейчас реально задеплоено под этим провайдером
        client-info.json
        <файлы состояния провайдера>
      history/<timestamp>/           # снапшоты для Rollback этого прокси
```

Старые версии хранили провайдер прямо на профиле сервера, а второй прокси
на том же хосте — отдельным "sibling"-профилем (`<имя>-<provider>`). При
первом запуске новой версии это **автоматически мигрирует**: sibling-и
сливаются в один сервер с несколькими прокси, файлы состояния переносятся
на новые пути — без вмешательства пользователя, без потери истории.

## proxy-scripts: как это устроено

```
proxy-scripts/
  deploy.sh              # универсальный: --provider <name> --host <ip>
  generate-config.sh      # универсальный диспетчер
  verify.sh                # универсальный диспетчер
  output/<провайдер>/      # всё сгенерированное: <ip>.yaml / <ip>.txt (ссылки), <ip>-client-info.json
  providers/
    shadowsocks-xray/
      remote/install.sh          # ставится и запускается на VPS
      remote/renew-hook.sh       # certbot deploy-hook (только при реальном продлении)
      remote/status-extra.sh     # доп. вывод для Status/Logs (сертификат/таймер)
      templates/clash-config.yaml.tmpl
      generate-config.sh
      verify.sh
    xray-reality/
      remote/install.sh
      remote/clients.sh          # list|add|remove|rename устройств (ключ на устройство) + перезапуск контейнера
      remote/clients.py          # логика clients.sh и рендер server.json / client-info.json
      remote/Dockerfile
      remote/start.sh
      templates/clash-vless.yaml.tmpl
      generate-config.sh
      verify.sh
```

### Универсальный слой не меняется, когда добавляется провайдер

`deploy.sh`, `generate-config.sh`, `verify.sh` в корне `proxy-scripts/` не
знают ничего о конкретном протоколе. Они узнают, что делать, из поля
`"provider"` внутри `client-info.json`, которое сам записывает
`install.sh` каждого провайдера:

```
proxy-scripts/generate-config.sh <client-info.json>
  → читает "provider" из json (например "xray-reality")
  → exec providers/xray-reality/generate-config.sh <client-info.json>
```

То же самое для `verify.sh`. `deploy.sh` определяет провайдера сразу из
флага `--provider`, а не из json (json на сервере ещё не существует до
первого деплоя).

### Контракт провайдера

Чтобы добавить новый провайдер (например WireGuard), нужно создать
`proxy-scripts/providers/<name>/` с:

- **`remote/install.sh`** — обязателен. Запускается на VPS как
  `SERVER_IP=<ip> install.sh`. Должен быть идемпотентным (повторный запуск
  не должен всё пересоздавать с нуля) и **обязан** в конце записать
  `/opt/proxy/<name>/client-info.json` с полем `"provider": "<name>"` —
  это единственное, что связывает `install.sh` с остальным конвейером.
  Имя Docker-контейнера должно совпадать с именем провайдера (`<name>`) —
  на этом держатся Status/Rollback/Remove в TUI.
- **`remote/*`** — любые другие файлы, нужные на сервере (Dockerfile,
  доп. скрипты) — всё из `remote/` заливается на VPS целиком.
- **`remote/clients.sh`** — опционально. Если есть, в карточке прокси
  появляются кнопки Devices / Add device / Remove device; `client-info.json`
  при этом содержит список `"clients": [{"name", "uuid"}]`.
- **`remote/status-extra.sh`** — опционально. Если есть, TUI запускает
  его в Status/Logs в дополнение к `docker ps`/`docker logs`.
- **`generate-config.sh <client-info.json> [output]`** — обязателен.
  Строит клиентский профиль (Clash Verge YAML и/или share-ссылку) из
  полей `client-info.json`.
- **`verify.sh <client-info.json>`** — обязателен. Внешняя проверка,
  специфичная для протокола; ненулевой exit code = провал.

Ничего в верхнеуровневых `deploy.sh`/`generate-config.sh`/`verify.sh`
трогать не нужно — они найдут новый провайдер сами по имени папки.

### Выбор порта

Оба провайдера читают переменную окружения `PROXY_PORT` при первой
установке: если она не задана — берут случайный порт в диапазоне
10000–60000, если задана — используют его. После первого успешного
`install.sh` порт фиксируется (сохраняется в `proxy.env` на сервере) и
дальше не меняется, даже если передать `PROXY_PORT` снова — чтобы сменить
порт, нужно сначала сделать Remove config.

- Через bash: `./deploy.sh --provider <name> --host <ip> --port 8443`
- Через TUI: поле "proxy port" в диалоге **Deploy new proxy** внутри
  карточки сервера

Любой новый провайдер должен поддерживать этот же контракт
(`"${PROXY_PORT:-$(( (RANDOM % 50000) + 10000 ))}"`), чтобы выбор порта
работал одинаково для всех.

### Несколько прокси параллельно на одном сервере

Это часть модели данных, а не отдельная настройка: у каждого провайдера
свой каталог (`/opt/proxy-scripts/<provider>`, `/opt/proxy/<provider>`) и
своё имя Docker-контейнера, поэтому они работают параллельно без
конфликтов. В TUI это одна карточка сервера с несколькими строками в
таблице прокси — добавляются кнопкой **Deploy new proxy**, находятся сами
через **Discover**.

Ограничение: **два экземпляра одного и того же** провайдера на одном
хосте не предусмотрены — пути и имя контейнера завязаны на имя
провайдера, а не на инстанс, повторный деплой того же провайдера
переустановит первый, а не создаст второй параллельно.

## Провайдеры сейчас

### `shadowsocks-xray`
Shadowsocks-libev + v2ray-plugin (websocket, TLS). Сертификат — Let's
Encrypt на `<IP>.sslip.io` через certbot (standalone HTTP-01, порт 80).
Авто-продление — системный таймер `certbot.timer` + deploy-hook, который
копирует новый сертификат и перезапускает контейнер **только** при
реальном продлении. UFW + fail2ban. Порт Shadowsocks — случайный
10000–60000.

Название в коде: `shadowsocks-xray` — по факту используется
**v2ray-plugin**, не Xray-core напрямую (это два разных, но родственных
проекта). Если понадобится сделать по-настоящему на Xray-core — это и
есть провайдер `xray-reality`.

### `xray-reality`
VLESS + TCP + Reality на Xray-core. Адаптация протокольных скриптов из
`amnezia-server-scripts` (Dockerfile и start.sh — почти без изменений;
генерация ключей и серверный `server.json` — свои, потому что у Amnezia
эта часть собирается в закрытом C++-коде приложения, а не в шелл-скриптах).

Особенность Reality: своего сертификата нет — нераспознанные TLS-запросы
прозрачно проксируются на настоящий "сайт-маскировку" (по умолчанию
`www.apple.com`, задаётся через `XRAY_SITE_NAME`; сайт должен поддерживать
TLS 1.3 и h2 и иметь небольшой handshake — `www.microsoft.com` не подходит:
его сертификат ~8 КБ не помещается в буфер Reality). Поэтому у этого
провайдера нет certbot/таймера продления, а `verify.sh` проверяет не
сертификат, а то, что маскировка TLS отдаёт настоящий сертификат
указанного сайта — сам VLESS-хендшейк без реального клиента не проверить.

Порт — случайный по умолчанию (как у shadowsocks-xray, см. "Выбор порта"
выше), но для Reality имеет смысл явно задать `PROXY_PORT=443`: смысл
Reality — маскировка под обычный HTTPS-трафик на стандартном порту 443;
на случайном высоком порту эта маскировка частично теряется — сервис
выглядит как "что-то на порту 47231", а не как обычный сайт.

### Ссылки для VPN-клиентов (Hiddify и др.)
`xray-reality` кроме Clash YAML формирует `vless://…security=reality…` —
по одной ссылке на каждое устройство (понимают Hiddify, v2rayN, v2rayNG,
Streisand, Karing и др.). Название профиля: `<сервер> · <устройство>`. Ссылки сохраняются в
`proxy-scripts/output/xray-reality/<ip>.txt` и печатаются в лог Deploy /
Regenerate config. Достаточно скопировать строку со ссылкой и добавить её
в клиент через «импорт из буфера».

`shadowsocks-xray` отдаёт только Clash YAML для Clash Verge: его
`v2ray-plugin` не понимают клиенты на sing-box (Hiddify и др. — ошибка
`plugin not found: v2ray-plugin`), поэтому share-ссылки для него нет.

### `mtproxy`
MTProto-прокси для Telegram в режиме FakeTLS (Docker-контейнер с
`mtproto-proxy`).

Вместо Clash-профиля отдаёт **ключ для подключения** — ссылки
`tg://proxy?server=…&port=…&secret=ee…` и `https://t.me/proxy?…`.
Они печатаются в лог (Deploy / Regenerate config) и сохраняются в
`proxy-scripts/output/mtproxy/<ip>.txt`. Ссылку достаточно открыть в
Telegram.

FakeTLS: домен-маскировка (по умолчанию `www.microsoft.com`, задаётся через
`MTPROXY_TLS_DOMAIN` при первой установке) зашит в секрет клиента
(`ee` + секрет + hex домена). Своего сертификата нет, продлевать нечего.
Секрет создаётся один раз и не меняется при повторном Deploy. Порт —
случайный по умолчанию; как и у Reality, лучше задать `PROXY_PORT=443`.
`verify.sh` проверяет доступность порта и TLS-ответ; сам MTProto-хендшейк
без Telegram не проверить.

## Тесты

```
.venv/bin/pip install -r requirements-dev.txt
.venv/bin/pytest -v
```

Ничего не трогает реальный `~/.config/ghosty-console` и не ходит по
настоящему SSH — вся сетевая часть подделана.

```
tests/
  conftest.py             # isolated_config (подмена ~/.config на tmp_path),
                           # автоочистка proxy-scripts/output/ после каждого теста
  fakes.py                 # make_fake_ssh_session(...) - подмена SSHSession
  sample_client_info.py    # готовые client-info.json для каждого провайдера
  test_config.py           # ghosty_console/config.py
  test_deploy.py           # ghosty_console/deploy.py (deploy/discover/regenerate)
  test_tui.py              # экраны TUI целиком, headless (Textual run_test)
  test_shell_syntax.py     # bash -n по каждому *.sh в proxy-scripts/ (авто-подхват)
```

Как добавить тест под новую фичу — не писать с нуля, взять шаблон из
док-строки в начале соответствующего файла (`test_config.py`,
`test_deploy.py` или `test_tui.py`) и подставить свои данные:

```python
def test_my_thing(isolated_config, monkeypatch):
    from ghosty_console import deploy as deploy_mod
    from ghosty_console.config import ServerProfile, add_server
    from tests.fakes import make_fake_ssh_session

    profile = ServerProfile(name="x", host="203.0.113.1")
    add_server(profile)
    monkeypatch.setattr(deploy_mod, "SSHSession", make_fake_ssh_session({...}))
    # ... deploy_mod.<function>(profile, "shadowsocks-xray", None, lines.append) ...
```

Важно:
- `isolated_config` — обязательная фикстура для любого теста, трогающего
  `ServerProfile`/`add_server`/`load_servers` — без неё тест будет читать
  и писать твой настоящий локальный список серверов.
- IP для тестовых данных — только из диапазона `203.0.113.0/24`
  (зарезервирован RFC 5737 для документации, никогда не настоящий адрес).
- Новый провайдер — тест синтаксиса `.sh`-файлов подхватится сам
  (`test_shell_syntax.py` сканирует `proxy-scripts/` рекурсивно), а тесты
  на `deploy()`/`discover()` можно скопировать из `test_deploy.py` и
  просто подставить `client-info.json` нового провайдера.

## Известные ограничения

- Живой прогон на реальном VPS проверен для обоих провайдеров лишь
